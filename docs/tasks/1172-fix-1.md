Owner decisions (2026-11-13, in chat):
- A pair where one side has `source = 'manual'` and both stays have identical `date_from` AND `date_to` is a duplicate entry: no alert, no mail.
- A pair that leaves the `current` set resolves its open alert on the next check (existing `for key := range open { if !current[key] ... ResolveAlert }` loop). So an already-open alert for such a pair resolves by itself; no extra code.

Verified facts:
- Manual stays have `reservation.source = 'manual'`. Found in `App/app/routes/admin.py:3904` (`"source": "manual",` in the `db.insert("reservation", {...})` of stay creation); default for other rows is `source TEXT NOT NULL DEFAULT 'ical'` at `App/app/db.py:197`. Other users of the value: `App/app/door_codes.py:176`, `App/app/onboarding.py:61`.
- `EnqueueMail` (`go/internal/ubyport/notify.go:326`) is idempotent by key. It first runs `SELECT id FROM email_outbox WHERE idempotency_key = $1` and returns the existing id if found; otherwise it INSERTs, and on unique violation `pgErr.Code == "23505"` it reads and returns the winner's id (doc comment: "An existing idempotency key returns its id; a unique-violation race returns the winner's id."). It uses no `ON CONFLICT`. `QueueDoubleBookingMail` passes the alert dedupe key as that key, so queueing it on every check never creates a second row.
- Resolved-then-reraised pair: the alert reopens, the outbox row from the first time still exists, so no second mail. This is intended; keep it.
