# 1200-fix-1: Explain the missing deadline watch on SQLite (Render staging)

Status: todo

## 1. Objective

Review finding on PR #964: Render staging (`render.yaml` `ubyhost-staging`: SQLite, `UBYHOST_ENABLE_SCHEDULER=1`, no Go service) now runs the stub `_job_deadlines_go_only` directly every 30 minutes. Staging gets a critical `job_failed:deadlines` card that never clears, and the `start()` warning fires only on PostgreSQL, so nothing explains it. Fix: staging accepts that it has no deadline watch, and says so.

## 2. Context

Tier A (filing path). Hard rule 1.

- `start()`: without PostgreSQL it logs one warning (no deadline watch runs here; the job runs only in the Go service) and does not schedule `deadlines` at all. A Go service needs PostgreSQL, so on SQLite the stub could only raise a card that never clears.
- On PostgreSQL nothing changes: `deadlines` is scheduled (enqueued for Go, or the stub runs directly and raises the critical alert when `UBYHOST_JOB_QUEUE_KINDS` lacks it). Production stays loud. The stub itself is unchanged.
- This overrides 1200 §2 "Kept untouched: the APScheduler entry" for SQLite only.
- `App/tests/test_job_queue.py`: the SQLite registration test expected every `JOB_KINDS` key scheduled; it now expects all but `deadlines` and checks the warning. The PostgreSQL test that queues every kind also checks `deadlines` is scheduled. `test_scheduler.py` ~166 (`check_deadlines` lambda) is a real guard that the stub never calls the old watch: left as is.
- One sentence in `docs/DEPLOYMENT.md` (Render staging paragraph). `docs/ENVIRONMENT.md` line 53 is not repeated (rule 9).
