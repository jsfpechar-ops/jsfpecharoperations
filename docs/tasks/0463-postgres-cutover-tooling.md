## 1. Objective
One script the owner runs on the server, `deploy/lightsail/scripts/pg-cutover.sh`, with three commands: `rehearse` (copy of production data into a throwaway database, verified, dropped), `cutover` (stop writes, backup, transfer, verify, switch `.env`, start, health check; any failure rolls back to SQLite by itself) and `rollback` (back to the untouched SQLite file). Plan: [migration-plan-v4](../plans/postgresql/migration-plan-v4.md) step 8. Owner steps: [owner-steps-cutover](../plans/postgresql/owner-steps-cutover.md).
## 2. Context
`App/scripts/sqlite_to_postgres.py --source <sqlite copy> --report <json> --expect-database <name> [--verify-only]` moves every table in one transaction, refuses a non-empty target, bootstraps the schema itself, and writes per-table row counts and typed hashes to the report; `--verify-only` recomputes them against the live target. The app switches backends by env: `UBYHOST_DATABASE_URL` set and `UBYHOST_DB` unset means PostgreSQL (`App/app/config.py`, both set is a startup error). Compose reads `deploy/lightsail/.env`. `restore.sh` already has the idioms for stopping `worker` then `ubyhost`, running one-off containers with `docker compose run --rm --no-deps`, and waiting for `/healthz`; `backup.sh` makes the encrypted snapshot. Litestream keeps replicating the SQLite file; it stays on until plan step 9. The managed database is Lightsail PostgreSQL (decision D1); the owner puts its URL in `.env` as `UBYHOST_PG_URL` (not `UBYHOST_DATABASE_URL`, so nothing changes until `cutover`).

## 4. Steps
1. `preflight` (run by every command): `.env` has `UBYHOST_PG_URL`; `/certs/rds-global-bundle.pem` exists, else download `https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem` into `deploy/lightsail/certs/`; a one-off container connects with the URL and prints `server_version_num` (must be ≥ 160000), `max_connections`, and the target database's table count (must be 0 for `cutover`).
2. `rehearse`: run `./scripts/backup.sh` (fails closed without a recipient: keep that); copy the database with `sqlite3 /data/ubyhost.db ".backup /data/pg-cutover/source.db"` inside the running `ubyhost` container, then `PRAGMA integrity_check` on the copy; `CREATE DATABASE ubyhost_rehearsal` through the master URL; run the transfer against the rehearsal URL (same URL, database name swapped) with `--expect-database ubyhost_rehearsal`, then `--verify-only`; print the per-table table from the report; `DROP DATABASE ubyhost_rehearsal`; delete the copy; keep the report at `/data/pg-cutover/rehearsal-<stamp>.json`.
3. `cutover`: refuse unless a rehearsal report with status ok is younger than 24 h; `backup.sh`; `docker compose stop worker ubyhost` (downtime starts; Caddy keeps answering); copy and integrity-check as in step 2 through a one-off container; transfer into the production database (`--expect-database ubyhost`), then `--verify-only`; on any failure: `DROP SCHEMA public CASCADE; CREATE SCHEMA public` on the target, `docker compose up -d ubyhost worker`, health check, exit 1 with the reason (SQLite was never written). On success: copy `.env` to `.env.sqlite-<stamp>`, rewrite `.env` so `UBYHOST_DB` is removed and `UBYHOST_DATABASE_URL=<UBYHOST_PG_URL>` added; `up -d ubyhost worker`; wait for `/healthz` like `restore.sh`; `curl` `/login` returns 200; on failure restore `.env` from the copy, `up -d`, health, exit 1. Print the downtime in seconds and where the SQLite file and `.env` copy are.
4. `rollback`: show the newest `.env.sqlite-<stamp>`, warn in one sentence that rows written to PostgreSQL since the cutover are not carried back, require the word `ROLLBACK` typed, restore `.env`, `up -d ubyhost worker`, health check.
5. Put the `.env` rewrite and restore in two shell functions and expose them as `env-switch <env-file> <url>` and `env-restore <env-file> <copy>` subcommands; test both in `App/tests/test_pg_cutover_script.py` on temp files (`UBYHOST_DB` gone and URL present after switch; byte-identical after restore; a file without `UBYHOST_PG_URL` makes `preflight` exit 2). Add `bash -n` of the script to that test.
6. Document the three commands in the two tables; nothing else in the docs.
