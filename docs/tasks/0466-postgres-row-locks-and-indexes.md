## 1. Objective
Part a: every query the worker runs on a timer is measured with `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL at 2,000-apartment volume, the missing indexes land as one goose file, and the iCal digest stops reporting every feed as changed (R-21). SQLite behaviour does not change in either part. Plan: [migration-plan-v4](../plans/postgresql/migration-plan-v4.md) step 11; R-01, R-19, R-21.
## 2. Context
- The lock: `App/app/db_postgres.py:708 _ensure_writer_lock()` runs `SELECT pg_advisory_xact_lock(WRITER_LOCK_ID)` (line 712) for `BEGIN IMMEDIATE` (line 551–562, via `_begin_immediate`), for every autocommit write `execute`/`executemany` opens (lines 579–582, 623–626), and before the per-statement savepoint inside an open transaction (lines 588–589, 632–633). Result: one writer at a time across web and worker, exactly SQLite's ceiling. Isolation is PostgreSQL's default READ COMMITTED.
- What it protects that nothing else does: a block that reads rows, decides in Python, then writes. Single conditional `UPDATE ... WHERE state = ?`, `INSERT ... ON CONFLICT`, and `DELETE` are atomic on PostgreSQL without it. The orchestrator classified all 27 `with db.immediate()` blocks plus `claim_sendable` (table in step 9). Filing correctness (rule 1) is the reason for every "lock" row: the write skew to prevent is `claim_sendable` (reporting.py:1329, a `db.cursor()` block: re-reads the guest, inserts the `submission_claim` lease) racing `mark_filed_by_hand` (reporting.py:2125: reads the claim, marks the guest filed). Under SQLite they serialise; under READ COMMITTED both can commit and the guest is filed by hand and on the wire.
- SQLite has no `FOR UPDATE`; the portable tool is an advisory transaction lock keyed by (name, id) on PostgreSQL and a no-op on SQLite, where `BEGIN IMMEDIATE` already serialises.
- Poll jobs (`App/app/scheduler.py:511–565`, intervals in `job_intervals()` line 74; `door_codes`, `push`, `guide_import` run every minute on main again since c935c55): `door_codes.reconcile` (door_codes.py:1172) + `cleaning.reconcile(all_owners=True)` (cleaning.py:60) + `cleaning_codes.process_queue` (cleaning_codes.py:166); `push.drain` (push.py:311); `guest_guide_import.process_queue` (381) + `guest_guide_merge.process_pending` (347); `mail.drain` (mail.py:643) + `claim.expire_holds` (claim.py:100) + `claim.sweep_reminders` (claim.py:780); `reporting.sweep` (reporting.py:1992); `icalsync.sync_all`. Existing indexes on these tables include `idx_door_code_due (state, next_attempt_at)`, `idx_push_outbox_due`, `idx_guide_import_status (status, id)`, `idx_outbox_state_attempt`, `idx_res_apartment_dates (apartment_id, date_from)`, `idx_submission_apartment`, `idx_cleaning_code_due`. Not indexed: `reservation` by status/date_to across all apartments (cleaning.reconcile, claim.sweep_reminders) and `reservation_claim` by state (expire_holds).
- R-21: the feed hash *is* stored (`ical_feed.body_sha256`, icalsync.py:681–688 skips an identical body). It never matches because `body_digest()` (icalsync.py:154) hashes the raw bytes, and Booking.com and Airbnb stamp `DTSTAMP` with the request time in every event, so the bytes differ on every fetch while no booking changed (production: `changed=8`, `created=updated=cancelled=0`).
- Local PostgreSQL: the commands in [0465 §2](0465-goose-migrations.md#2-context); for part a start the server with `-o "-k /tmp/pgt/sock -p 55433 -c listen_addresses='' -c log_min_duration_statement=0 -c log_parameter_max_length=-1"`.

### Part b
6. `App/app/db.py`, after `immediate()` (line 951): add
```python
def lock_key(cur, name: str, key: int) -> None:
    """Serialise writers of one row (name, key) until this transaction ends.

    PostgreSQL only; on SQLite BEGIN IMMEDIATE already holds the one write lock.
    Take several keys in ascending order to rule out deadlocks.
    """
    if getattr(config, "DB_BACKEND", "sqlite") != "postgresql":
        return
    cur.execute("SELECT pg_advisory_xact_lock(hashtext(?), ?)", (name, int(key)))
```
   It must run inside an open transaction (`db.immediate()` or `db.cursor()` block); `lock_timeout` is the connection's existing 30 s.
7. `App/app/db_postgres.py`: `BEGIN IMMEDIATE` executes plain `BEGIN` and sets `SET LOCAL lock_timeout` only (no advisory lock); the autocommit and savepoint branches of `execute` and `executemany` no longer call `_ensure_writer_lock` (keep the `BEGIN`, savepoint and rollback logic exactly as is). Delete `_begin_immediate`, `_ensure_writer_lock`, `_transaction_lock_reset`, `_writer_lock_held` and their calls. Keep `WRITER_LOCK_ID`, `acquire_writer_session_lock` and `release_writer_session_lock` (schema apply and the transfer still use them; both run with the app stopped).
